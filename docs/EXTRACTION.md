# Finding Extraction

This document describes the tooling that extracts and generates
findings from benchmark PRs during corpus construction. It covers
four producer types: human review comments and inferred author actions
(extracted from the PR's history, METHODOLOGY.md §4.1), and LLM review
passes and deterministic tools (generated by running analysis against
the PR, METHODOLOGY.md §4.2). Human comments and inferred author
actions form the backbone of the golden set; LLM passes and
deterministic tools supplement them with broader coverage.

The output of extraction is a set of raw findings per PR, ready for
classification (METHODOLOGY.md §5) and deduplication (§5.4).

Producer-specific filters below limit what is extracted or generated; they
are not TP/FP criteria. The classifier evaluates every retained finding
independently at the review-time SHA, including findings outside the diff,
with scope recorded separately.

## 1. Input

Extraction operates on the PR manifest described in HARNESS.md §2. For
each PR, the extractor needs:

- The repo URL and PR number.
- The base and head commits (the review-time snapshot).
- Access to the GitHub API for fetching review comments and commit
  history.

Corpus construction uses the 219-PR public full corpus. The 25-PR test corpus
is included within it and may be used for smaller extraction and validation
runs with the same process.

The extractor also needs the full commit history of the PR — the
sequence of commits between the PR's opening and its final state
(merged, closed, or abandoned). This includes commits pushed after the
review-time head commit, which are used for inferring author actions
but are not part of the review-time diff.

## 2. Human Review Comments

### 2.1 What We Extract

Every line- or range-anchored review comment authored by a human
reviewer on the PR. Each comment becomes one finding.

PR-level comments (comments not anchored to a specific line) are
recorded as metadata but are not extracted as findings, since they
cannot be assigned a file path and line range.

### 2.2 Comment–Snapshot Alignment

Review comments on a PR may be anchored to different commits. The
manifest records a single head commit per PR — the commit with the
most review comments, which represents the state of the code that
attracted the most reviewer attention. Comments anchored to other
commits are not automatically discarded; they are included if the
issue they describe is still present at the chosen head.

Comments fall into three categories:

1. **On the chosen head.** The comment's `commit_id` matches the
   manifest head. These are included directly — file path and line
   range are already correct.

2. **On a different commit, code unchanged.** The comment is
   anchored to a different commit, but the file and line region it
   references are identical at the chosen head. These are included
   with line numbers mechanically remapped using `git diff` between
   the comment's commit and the chosen head.

3. **On a different commit, code changed.** The comment is anchored
   to a different commit, and the code at the referenced region has
   changed at the chosen head. These are included with best-effort
   line remapping and flagged as `alignment: "code_changed"`. The
   classifier (METHODOLOGY.md §5) will determine whether the issue
   described in the comment is still present — if the code was fixed,
   the classifier labels the finding FP; if the issue persists, TP.

This alignment process ensures that comments from the full review
history are preserved rather than only those on the chosen commit.
The classifier handles the validity question rather than requiring
a separate LLM validation step during extraction.

#### Alignment Steps

1. For each comment not on the chosen head, compute `git diff`
   between the comment's `commit_id` and the manifest head for the
   affected file.
2. If the file does not exist at the chosen head, drop the comment.
3. If the comment's line region is outside the diff (unchanged),
   remap line numbers mechanically and include the comment.
4. If the comment's line region has changed, include the comment
   with best-effort line remapping and flag it as `code_changed`.

This keeps extraction simple and deterministic — no LLM calls are
required during the extraction step.

### 2.3 Extraction Steps

1. Fetch all review comments on the PR via the GitHub API
   (`GET /repos/{owner}/{repo}/pulls/{pr_number}/comments`).
2. Filter to comments authored by human users (exclude bot accounts).
3. For each comment, extract:
   - **File path** — from the comment's `path` field.
   - **Line range** — from `line` and `start_line` (for multi-line
     comments) or `line` alone (for single-line comments). Map these
     to the diff-side line numbers using the comment's `side` field.
   - **Message** — the comment body, in markdown.
   - **Author** — the GitHub username of the commenter.
   - **Comment URL** — for traceability.
   - **Created at** — the timestamp, used to determine which comments
     preceded which commits.
4. Discard comments that are part of a reply thread where the parent
   comment is already extracted, unless the reply raises a distinct
   issue. In practice, treat each top-level review comment as a
   finding and attach replies as context rather than separate findings.
5. For comments not anchored to the chosen head commit, run the
   alignment process described in §2.2 to determine whether the
   comment should be included and to remap line numbers.

### 2.4 Edge Cases

- **Outdated comments.** GitHub marks review comments as "outdated"
  when subsequent commits change the lines they reference. These
  are handled by the alignment process in §2.2: the comment is
  included with a `code_changed` flag and the classifier determines
  whether the issue is still present.
- **Resolved conversations.** Comments marked as resolved are still
  extracted. Resolution is evidence that the finding was addressed,
  which is useful signal for the classifier.
- **Review verdicts.** Comments attached to a formal review
  (approve, request changes, comment) are extracted individually.
  The review verdict itself is recorded as metadata on each finding
  from that review.

## 3. Inferred Author Actions

### 3.1 What We Infer

When a PR author pushes a follow-up commit that fixes an issue in
code that was part of the review-time diff, we infer a finding
describing the issue that was fixed. The goal is to capture issues
the author recognized and addressed — whether prompted by a reviewer
comment, verbal feedback, or their own re-reading of the code —
even when no explicit review comment exists.

Not every follow-up commit implies a finding. Some follow-up commits
add new functionality, resolve merge conflicts, or make unrelated
changes. The inference step must distinguish fixes to reviewed code
from other kinds of changes.

### 3.2 Identifying Follow-Up Commits

1. Fetch the full commit history of the PR.
2. Identify the review-time head commit (from the manifest).
3. All commits after the review-time head commit are follow-up
   candidates. If the PR was merged, these are the commits between
   the review-time head and the merge commit. If the PR was closed
   or abandoned, these are all subsequent commits on the PR branch.
4. Filter to commits authored by the PR author. Commits by other
   contributors (e.g., co-authors, maintainers pushing fixes) are
   excluded — they represent a different kind of signal.

### 3.3 Identifying Changed Regions

For each follow-up commit:

1. Compute the diff introduced by the commit (the commit's own
   diff, not the cumulative diff against base).
2. Identify which files and line ranges the commit modifies.
3. Check whether the modified regions overlap with the review-time
   diff (the diff between base and head). Only modifications to
   code that was part of the reviewed change are candidates for
   inference. Changes to new files or previously-untouched regions
   are not — they represent new work rather than fixes to reviewed
   code.

### 3.4 LLM-Assisted Inference

For each follow-up commit that modifies reviewed code, an LLM
generates the inferred finding. The LLM receives:

- The review-time diff for the affected file(s), restricted to the
  relevant hunks — the code as the reviewer would have seen it.
- The follow-up commit's diff for the same region — what the author
  changed.
- Any human review comments anchored to the affected lines or
  nearby lines, if they exist. These provide context for why the
  author made the change, but the LLM is instructed to describe
  the underlying issue in the original code, not to restate the
  reviewer's comment.

The LLM is prompted to:

1. Determine whether the follow-up change is a **fix** to an issue
   in the reviewed code, or something else (new functionality,
   style cleanup, unrelated refactor). If it is not a fix, no
   finding is emitted.
2. If it is a fix, describe the issue that existed in the
   review-time code — what was wrong, where, and why it matters.
   The description should stand alone as a review finding: it
   should be understandable without seeing the fix.
3. Assign a file path and line range anchored to the review-time
   diff (not the follow-up commit's lines).

The output is a candidate finding or a determination that no finding
should be emitted.

### 3.5 Linking to Review Comments

After inference, each inferred finding is checked against the
human review comments extracted in §2:

- If a review comment exists on the same or overlapping lines and
  describes the same issue, the inferred finding is linked to that
  comment. This creates corroborating evidence: the reviewer flagged
  it and the author fixed it. The two are not deduplicated at this
  stage — deduplication happens during golden set construction
  (METHODOLOGY.md §5.4).
- If no matching review comment exists, the inferred finding stands
  alone. These are the most valuable inferred findings: they
  represent issues the author addressed without explicit prompting.

### 3.6 Conservative Filtering

Not every LLM inference is worth keeping. Before the inferred
finding enters the corpus:

- **Confidence gate.** The LLM is asked to rate its confidence that
  the follow-up change is genuinely fixing an issue (as opposed to
  extending, refactoring, or polishing). Low-confidence inferences
  are discarded.
- **Scope check.** The inferred issue must be in code that was part
  of the review-time diff. Issues in surrounding context that the
  author happened to fix while they were in the file are out of
  scope for inference (they may still be valid findings, but they
  cannot be attributed to the review process).
- **Triviality filter.** Pure whitespace, formatting, or import-order
  changes are not inferred as findings, even if they technically
  modify reviewed code.

## 4. LLM Review Passes

LLM-based review agents are run against the review-time diff to
surface findings that human reviewers and author actions may have
missed. Because LLM producers risk biasing the golden set toward
the models used to generate them, the strategy is to maximize
diversity across models, prompts, and context.

### 4.1 Diversity Strategy

No single model-prompt combination should dominate the golden set's
LLM-produced findings. Diversity is pursued along three axes:

**Model diversity.** Use at least 2–3 different base models (e.g.,
Claude, GPT, Gemini). Each model family has different attention
patterns and blind spots. A finding surfaced independently by two
different model families is stronger evidence of a genuine issue
than one surfaced by only one.

**Prompt diversity.** Rather than one broad "review this PR" prompt,
run targeted passes that each emphasize a different concern area:

- Correctness and logic errors.
- Error handling, edge cases, and failure modes.
- Security and input validation.
- Concurrency and state management.
- API design and interface concerns.

The goal is not to generate more findings per pass, but to probe
regions of the finding space that a single general prompt would
under-explore.

**Context diversity.** Run passes with varying levels of context:

- Diff only — what a reviewer sees at first glance.
- Diff plus surrounding file context — enough to understand local
  control flow and data dependencies.
- Diff plus related files (callers, callees, tests) — enough to
  assess cross-cutting concerns.

Findings that require broader context tend to be the higher-level
architectural observations that are hardest to surface and most
valuable in the golden set.

### 4.2 Execution

For each PR and each (model, prompt, context) combination:

1. Assemble the input: the review-time diff, any surrounding
   context required by the context level, the PR title and body.
2. Call the model with the targeted prompt.
3. Parse the output into individual findings, each with a file
   path, line range, and message.

Each finding records which model, prompt variant, and context level
produced it.

### 4.3 Controlling Volume

Multiple passes across multiple models can generate a large number
of findings per PR. This is managed by:

- **Deduplication during golden set construction** (METHODOLOGY.md
  §5.4) — findings from different passes that describe the same
  underlying issue are collapsed.
- **Classification** — one Claude Sonnet 5 classifier labels every finding
  TP/FP and assigns severity, category, and the other auxiliary labels.
  Low-quality findings are identified by the labels; redundant findings
  are handled separately by deduplication, not treated as FPs merely
  for repeating another finding.
- **Per-producer ablation** (METHODOLOGY.md §10) — contribution
  of each (model, prompt) combination can be measured and passes
  that add little incremental value can be dropped.

### 4.4 Bias Monitoring

For each PR, track the producer distribution of the golden set:
what fraction of golden TPs came from each producer type (human,
inferred, LLM, deterministic) and, within LLM, from each model.
If any single LLM producer contributes more than a target threshold
of the golden TPs (after deduplication), that is a signal to either
add more diverse producers or down-weight that producer's unique
findings.

The leave-one-out ablation (METHODOLOGY.md §10) is the definitive
test: if removing a single LLM producer substantially changes a
candidate agent's recall score, the golden set is over-reliant on
that producer.

## 5. Deterministic Tools

Linters, type checkers, and static analyzers are run against the
review-time diff to surface findings with high mechanical precision.
These tools are reliable for certain classes of issues (type errors,
unreachable code, known bug patterns, security rules) but tend to
produce high volumes of low-severity style and formatting findings
that would skew the golden set toward pedantic concerns.

### 5.1 Tool Selection

Include tools that target substantive issues: bug finding, type
errors, security vulnerabilities, and dataflow problems. Exclude or
restrict tools that primarily target style and formatting. If a tool
has both substantive and stylistic rules, configure it to run only
the substantive subset.

#### Cross-Language Tools

These are run across all languages in the benchmark:

- **Semgrep** — security and bug-pattern rules. Run with the
  `p/security-audit` and `p/bugs` rulesets. Covers Java, Python,
  C#, TypeScript, JavaScript, Go, and most other languages.
- **CodeQL** — deep dataflow analysis, taint tracking, and security.
  Slower to run but finds issues that surface-level tools miss.
  Covers Java, Python, C#, TypeScript, JavaScript, Go, Ruby, Swift,
  and Kotlin.

#### Java

- **ErrorProne** — bug patterns, concurrency issues, common mistakes.
  Google's compiler plugin with a very low false positive rate.
- **SpotBugs** — null dereference, resource leaks, bad practice.
  Bytecode-level analysis (successor to FindBugs).

#### Python

- **Pyright** — type errors, unreachable code, missing returns.
  Run in strict mode for maximum coverage.
- **Ruff** — fast linter with pyflakes-derived bug-finding rules.
  Must be configured to exclude stylistic rules; enable only the
  `F` (pyflakes), `E` (errors), and `B` (bugbear) categories.
- **Bandit** — Python-specific security vulnerability scanner.

#### C\#

- **Roslyn analyzers** — null reference, disposal, async misuse.
  Built into the .NET SDK. Enable the `CA` (code analysis) and
  `IDE` (code quality) rule sets; disable formatting rules.

#### TypeScript and JavaScript

- **TypeScript compiler** (`tsc --noEmit`) — type errors and
  unreachable code. Only applicable to TypeScript. Use the
  strictest settings (`strict: true`).
- **ESLint** — must be restricted to bug-finding rules only.
  Enable `possible-errors` and `possible-problems` categories;
  disable all stylistic, formatting, and layout rules.

#### Go

- **go vet** — printf format mismatches, unreachable code, copy
  lock violations. Ships with Go and has a very low false
  positive rate.
- **Staticcheck** — the standard Go static analyzer for
  substantive issues: bug finding, deprecation, performance.
- **govulncheck** — known vulnerabilities in dependencies.

#### Other Languages

For languages outside the core set, rely on Semgrep and CodeQL.
Both have broad language coverage. Add language-specific tools
only if coverage gaps appear during golden set construction.

### 5.2 Execution

1. Check out the review-time head commit.
2. Run each configured tool against the changed files.
3. Collect the tool's output (typically in a structured format
   like SARIF, JSON, or the tool's native output).
4. Filter to findings that target lines within the review-time
   diff. Findings on unchanged lines are discarded.

### 5.3 Severity Filtering

After labeling (METHODOLOGY.md §5), deterministic tool findings labeled
low severity are excluded from the golden set.
This is a pragmatic choice: low-severity linter findings are
the category most likely to flood the golden set with noise and
least likely to represent issues a human reviewer would flag.
Medium and high severity findings from deterministic tools are
retained.

### 5.4 Output

Each finding records the tool name and rule ID in its source block:

```json
{
  "producer": "deterministic_tool",
  "file": "src/pool.go",
  "start_line": 15,
  "end_line": 15,
  "message": "Error return value of `conn.Close()` is not checked",
  "source": {
    "type": "tool",
    "tool": "errcheck",
    "rule_id": "unchecked-error"
  }
}
```

## 6. Output

For each PR, the extractor writes a file containing all extracted
findings. The format mirrors the harness output (HARNESS.md §8):

```json
{
  "pr": {
    "repo": "https://github.com/org/repo",
    "pr_number": 1234,
    "base": "abc123def",
    "head": "456fed789"
  },
  "findings": [
    {
      "producer": "human_review",
      "file": "src/pool.go",
      "start_line": 42,
      "end_line": 45,
      "message": "This access to pool.conns is not protected by the mutex",
      "source": {
        "type": "review_comment",
        "author": "reviewer-username",
        "url": "https://github.com/org/repo/pull/1234#discussion_r12345",
        "created_at": "2026-03-15T14:30:00Z"
      }
    },
    {
      "producer": "inferred_author_action",
      "file": "src/pool.go",
      "start_line": 78,
      "end_line": 82,
      "message": "The error from conn.Ping() is discarded, masking connection failures",
      "source": {
        "type": "follow_up_commit",
        "commit": "789abc012",
        "linked_comment_url": null
      }
    }
  ]
}
```

Each finding records its `producer` type and a `source` block with
provenance information. The `source` block varies by producer type
and enables traceability back to the original review comment or
commit.

Output files are written to:

```
extraction/
  {repo_name}/
    {pr_number}-{head_sha_prefix}.json
```

These files are the input to classification (METHODOLOGY.md §5) and
golden set construction (§5.4).

## 7. Operational Notes

**GitHub API rate limits.** Extracting comments and commit history
requires multiple API calls per PR. For large benchmark runs, use a
GitHub token with sufficient rate limits and implement backoff/retry.
Comment and commit data can be cached locally after first fetch since
the review-time snapshot is immutable.

**LLM cost.** Each follow-up commit that touches reviewed code
requires an LLM call for inference (§3), and each (model, prompt,
context) combination requires a call for LLM review passes (§4).
For a typical PR with 2 follow-up commits and 6 LLM pass
combinations, this is roughly 8 LLM calls per PR. The inference
and review-pass LLMs do not need to be the same models used for
classification or matching.

**Incremental extraction.** If new PRs are added to the manifest,
extraction only needs to run on the new entries. Existing extraction
results are stable since they depend only on the immutable review-time
snapshot and commit history.
